# Foundation implementation decisions

These decisions implement B02–B04 against PRD v2.1. They refine the approved architecture without changing the product scope. The implementation contains one skill and no website, service, product CLI or live verifier.

## Canonical fields: AT-01 resolved

PRD §9.2 defines the serialized entity contracts. The illustrative examples in §14.1–§14.2 are not a second format. Schemas reject extra fields, missing canonical fields and obsolete status aliases; there is no silent migration layer.

| Illustrative shorthand | Canonical representation |
|---|---|
| Claim `id` | `claim_id` |
| Claim `property` | `predicate` |
| Claim `network: mainnet` | `network_id: qie-mainnet` |
| Claim `risk` | `risk_level` |
| Claim `last_checked_at` | `checked_at` |
| Claim `runtime_validator` | A relevant `ValidationRun.scope.operation` linked through `evidence_test_ids`; no alias field |
| Capability `id` | `capability_id` |
| Capability `product` | `tool_id` |
| Capability `networks` | `network_ids` |
| Capability `integration_recipe` | `recipe_path` |
| Capability `last_checked_at` | `checked_at` |
| Capability `validation_test_id` | `evidence_test_ids`, an array |

All enumerated entity fields are required keys. Unknown timestamps, publication dates, content hashes, licenses, owners, versions and recipe locations are explicit `null` where allowed. An absent evidence list is `[]`. Null never means verified or current. Claim `value` supports scalar facts in this slice; known network predicates additionally validate integer chain IDs and HTTPS URLs. Complex future claims require an explicit schema extension.

Schema `$id` URIs use the reserved `qie-forge.invalid` identifier namespace. Ajv resolves them from the local schema collection; they are not an HTTP service or a new API.

Addresses use the compound identity `(chain_id, lowercase(address), claimed_product)` instead of an invented ID alias. `expires_at` extends §9.2's AddressRecord to satisfy §9.4 freshness requirements. Code observations bind to a network-scoped validation run; verified identity additionally requires issuer and ABI provenance, reviewed matching code evidence, and check/expiry metadata. The canonical address and runtime evidence collections are empty. Synthetic unit fixtures are not added to them.

The standalone helper uses `live_check.outcome`, not §14.3's illustrative `status: NOT_RUN`. `NOT_RUN` is a run outcome; it is never a claim or capability status. Since B06, action-proof reports from §14.4 also exist as a separate channel (`scripts/lib/transaction-diagnostic.mjs`, field names per §14.4); see the B06 decisions below.

## Evidence and policy contract

The canonical status enum is exactly `VERIFIED`, `DOCUMENTED`, `CLAIMED`, `UNKNOWN`, `CONFLICTED`, `STALE`, `UNSUPPORTED`, `DEPRECATED`. Evidence types and run outcomes use their separate PRD enums. Marketing alone cannot establish a documented technical capability. Negative statuses require explicit source evidence; absence of proof stays UNKNOWN.

VERIFIED promotion requires sources, explicit validity, relevant reviewed non-mock PASS evidence, matching network, operation and exact tool version, matching expected/observed results, and, for claims, equality to the claimed value. Record freshness cannot start after its supporting check. A code-presence check cannot prove issuer identity. These checks enforce evidence structure; they do not independently establish that a human reviewer or artifact is authentic. Maintainer review remains required.

`tool_version_range` retains the PRD field name, but **VERIFIED currently accepts only the exact tested version string** through equality with `ValidationRun.tool_version`. No semver range solver or blanket compatibility claim is implemented. Test scopes use `MOCK`, `LOCAL_REPLAY`, and `CHAIN_OBSERVATION`; these are not statuses.

The v1 policy schema freezes precedence with CONFLICTED first, requires explicit expiry for VERIFIED, and requires live checks before writes. Expired positive evidence projects to STALE; missing/unusable clock, future check metadata or offline high-risk VERIFIED evidence projects to UNKNOWN. Stored blocking states remain blocking. The pure evaluator never promotes evidence and is copied unchanged into the skill. There are no invented TTLs: expiry is explicit per record until maintainers establish risk-specific policy. Multi-source conflict adjudication and browser parity belong to later work; this slice consumes an explicitly curated conflict status.

Operational network IDs are restricted to `qie-mainnet` and `qie-testnet`. `qie-native` and `general` are permitted **navigation scope labels**, not operational network IDs. Native/bridge/indexer capabilities whose actual network is unknown use an empty `network_ids` list and UNKNOWN. No native chain identity or EVM compatibility is inferred.

## Build and installation: AT-02 partly resolved

Node 24.20.0, npm 11.19.0, Skills CLI 1.7.2, Ajv 8.20.0, ajv-formats 3.0.1 and yaml 2.9.1 were installed/executed as recorded in the results. Product users need only the installed bundle; the helper imports Node built-ins and a local module. Dependencies are development tools, not installed skill dependencies.

Frozen `release-context.json` supplies `built_at`; there is no wall-clock read in packaging. Selected records and their transitive sources/tests become a sorted JSON snapshot. `sources_checked_at` is the oldest included source review or null if incomplete. Its input-context field must remain null because the builder derives the per-skill aggregate from canonical sources. Source review timestamps are not live RPC timestamps. Every packaged file except the manifest itself has a SHA-256 entry. Snapshot and policy hashes are independently checked. Same inputs/context produce equal bytes across separate roots.

Private `SKILL.md.in` authoring prevents the installer from discovering unfinished source entries. The only discovery entry is generated `skills/qie-networks/SKILL.md`. Staging and publication contain identical bytes. Generated Markdown is marked DO NOT EDIT; executable helpers preserve valid comments, and JSON provenance is recorded in the manifest. Cross-references must resolve within the skill; recipe pointers cannot point to a missing local file. No sibling-root fallback exists.

The link checker supports this foundation's controlled Markdown syntax: inline links/images and explicit reference definitions/usages. It also checks static module imports and literal `new URL(..., import.meta.url)` data paths. It is not a general CommonMark parser or arbitrary-program dependency analyzer. No HTML renderer is needed yet; the architecture's Markdown renderer dependency is deferred until the website. New syntax or dynamic imports require an intentional checker change and fixture.

Actual Skills CLI tests prove local source discovery, suite/single selection, copied/symlinked agent targets, and operation after source deletion. Published Git source/ref installation, update/rollback and actual Codex/Claude/Cursor/OpenCode journeys remain unverified. A tagged release cannot be tested before a repository/ref exists. Official `skills-ref` validation could not run because the validator is unavailable locally and shell DNS cannot reach PyPI. This remains a distribution gate, not an equivalent check silently replaced by our validator.

## B05 decisions: router packaging, release metadata and routing fixtures

B05 generalizes the B04 vertical slice into a multi-skill builder and adds the original `qie` router. The canonical-data model did not change; the packaging contract gained one explicit selector and one explicit manifest pointer.

**Per-skill generated artifact.** Each catalogue entry in `knowledge/skills.yaml` now carries exactly one `generated_references` choice: `network-profiles` (the qie-networks slice: `data/network-claims.json` plus mainnet/testnet references) or `coverage` (the router slice: `data/qie-a-z.json` plus generated A–Z coverage map and routing table). Both artifact sets provide the skill's knowledge snapshot, so every manifest digest check works identically. `MANIFEST.json` records the artifact through the new required `snapshot_path` field; bundle validation resolves the knowledge digest through that pointer instead of a hardcoded filename. The skill and manifest schemas gained the corresponding required fields; `schema_version` is therefore `1.1.0`, with the policy schema frozen to the same version.

**Catalogue-derived router references.** The router's `references/qie-a-z.md`, `references/routing.md` and `data/qie-a-z.json` are generated from the existing canonical catalogue (domains, sources, capabilities, skill selectors, policy). The router skill snapshot contains no claims: chain IDs, RPC endpoints and explorers stay in `qie-networks`, and a test asserts the router files never restate the mainnet/testnet chain IDs or link into sibling skill directories. D01 and D12 now name `qie` as their released entry skill. The router's `logical_handoffs` list only skills that are actual routes in the canonical catalogue; the PRD's P1 taxonomy names (for example `qie-defi`, `qie-security`) are not catalogue routes today and are not listed as handoffs.

**Missing topical skills.** Publication state is derived from the canonical catalogue selector (`enabled_for_release`), never from a domain's mention of a skill. Generated references label three states precisely: `published in this release` (installable; may simply be missing locally), `catalogued; not published in this release` and `planned; not a published artifact` (both NOT installable and never offered as release artifacts). The router entry splits remediation accordingly: a published-but-missing skill can be installed from the same QIE Forge source (`skills add <qie-forge-source> --skill <skill-name>`); a planned or unpublished skill must be declared non-installable with no install command offered. No repository namespace is invented while D-02 remains open, so the remediation command uses an explicit placeholder instead of a fabricated `OWNER/qie-forge`. A regression test disables an entry-skill selector and asserts the generated routes stop presenting it as published.

**Release metadata consistency.** The frozen `release-context.json` previously carried a `built_at` earlier than the source `reviewed_at` timestamps included in its own manifests. `built_at` is now `2026-10-19T01:00:00Z` (after the `2026-10-19T00:08:45Z` source reviews), release `0.2.0-router.1`, and `validateKnowledge` rejects any release context whose `built_at` precedes a source review timestamp; the builder independently refuses a derived per-skill `sources_checked_at` that follows `built_at`. A release cannot claim to embed source reviews that had not happened when it was cut.

**Routing fixtures are a frozen contract, not a model evaluation.** `tests/fixtures/routing-fixtures.json` freezes 23 intent fixtures (7 high-risk) with accepted domain/skill route sets, network scope, EVM/native/general execution context, forbidden substitutions and — for high-risk fixtures — a required router behavior string. `tests/routing.test.mjs` verifies each fixture against the built bundle: route consistency with the catalogue, mainnet/testnet scope containment, native-vs-EVM scope separation, forbidden-route absence, published routing-table rows and the required router safety behaviors. This proves the catalogue/router contract deterministically. Whether a coding agent selects these routes under real prompts (FR-002's ≥90%/100% targets) remains a separate cross-host evaluation (B13); these fixtures are its frozen input set.

## B06 decisions: shared-status read-only diagnostics

B06 extends the shared status prerequisite into scoped, read-only live-check helpers before operational recipes (FR-003, FR-007, FR-009, FR-020). No status in the canonical data changed: every capability stays UNKNOWN, every claim stays DOCUMENTED, and the helpers produce observations, never evidence promotion.

**One transport, five hardening rules (audit F-05).** `scripts/lib/rpc.mjs` performs one request per call on the injected or global fetch transport: no signing, no broadcasting, no keys, no retries, no cross-endpoint or cross-network fallback. Responses are read under a hard byte ceiling that counts UTF-8 bytes while streaming (an oversized reply is rejected mid-stream, not after buffering); every reply must declare JSON-RPC 2.0, echo the request ID, and carry exactly one of `result`/`error`; the server-side "method not found" class maps to `UNSUPPORTED_PROVIDER`, everything else to `RPC_UNAVAILABLE`, rate limits to `RPC_RATE_LIMITED`, unparsable payloads to `RPC_MALFORMED`. Timeouts are bounded at 10 seconds via `AbortSignal.timeout`.

**Read-only network preflight (FR-003).** `scripts/lib/network-diagnostic.mjs` verifies `eth_chainId` and block responsiveness on one explicitly selected network, using the packaged documented endpoint by default or an explicit `--rpc` override that is re-verified against the packaged chain ID. Outcomes are explicit: identity mismatch → `FAIL`/`WRONG_CHAIN` and stop (the other network's endpoint is never tried); offline, timeout, 429, malformed JSON/quantities, malformed block headers or block height zero → `UNKNOWN` with the matching error class; a matched chain plus a nonzero block → `PASS` with two standing warnings — a live observation never promotes a claim or capability, and freshness is never claimed (no reviewed risk-based threshold exists; AT-06 stays open). The report embeds `effective_claims`, computed by the shared evaluator on the same clock as `checked_at`, so expired VERIFIED evidence projects to STALE even when the live observation passes (FR-020).

**Authoritative network-to-chain binding (audit F-02).** `scripts/lib/transaction-diagnostic.mjs` does not accept a caller-chosen chain ID: the binding comes from the packaged, schema-validated network profile for the selected network. A supplied `expectedChainId` that disagrees with the packaged value is a usage error, and the CLI exposes no chain argument at all. A testnet-labelled task pointed at a mainnet chain reply produces `WRONG_CHAIN` after exactly one request and never reads mainnet receipts.

**Strict receipt and code evidence (audits F-03/F-04).** A receipt must echo the requested transaction hash, carry a 32-byte block hash, a hex block-number quantity, exactly one of call-target/created-contract (well-formed addresses), and a canonical status field — anything else is `RPC_MALFORMED` with `inclusion` staying UNKNOWN; `PASS` is awarded only to fully shape-checked receipts. Runtime code is accepted only as nonempty, even-length `0x`-prefixed hex bytecode; a valid empty response (`0x`) is `CONTRACT_NO_CODE`/FAIL, and malformed code output is UNKNOWN rather than a false PASS. A passing code read carries an explicit warning that the observation is at the latest block, not pinned to the inclusion block, and that code presence never proves issuer identity (the address-identity release blocker below stands unchanged).

**Two output channels, one schema family.** The live-check channel keeps the snake_case report with `live_check.outcome`; the transaction channel uses the §14.4 field names (`checks.inclusion/execution/identityLinkage/applicationEffect/finality`, `applicationOutcome`, `limitedObservation: CONFIRMED_AT_BLOCK` when every scoped check passes). Three schemas were added: `error-code.schema.json` (the fourteen §14.5 classes), `live-check.schema.json` and `evidence-report.schema.json` — now fifteen schema files total. The evidence channel freezes `finality` to UNKNOWN and makes `APPLICATION_VERIFIED` structurally unreachable: the schema forces VERIFIED onto a passing finality check that cannot exist in this version, so a forged VERIFIED outcome fails validation (tested explicitly). The stable error class first recorded is preserved and later conflict reasons move into warnings.

**Bundling and invocation boundaries (audit F-01).** `qie-networks` ships `verify-network.mjs` plus `lib/network-diagnostic.mjs`, `lib/rpc.mjs` (and the pre-existing evaluator), so a single-skill install performs its own preflight with no repo-root dependency. `verify-transaction.mjs` and the transaction library remain source-side until `qie-transactions` exists in B07; its bundle will have to include the network-claims snapshot. Source CLIs cannot read a nonexistent root `data/` directory — they are bundle-only by default, and both accept an explicit `--claims <network-claims.json>` override so maintainers can run them from the checkout against a named snapshot. Exit conventions differ on purpose: the preflight CLI is fail-closed (0 PASS, 1 FAIL/UNKNOWN, 2 usage) so `&&` chains cannot proceed on a bad preflight; the transaction CLI reports any completed observation with 0 (its verdict fields are authoritative) and 2 for usage errors.

**Negative paths are frozen fixtures, all mocked (audits F-06/F-05 tests).** `tests/transaction-diagnostic.test.mjs` freezes 21 negative fixtures (exceeding FR-007's minimum of twelve): wrong chain, unavailable/rate-limited/malformed JSON-RPC and chain data, fabricated and pending transactions, reverted creations, mismatched or absent created addresses, empty/malformed/odd-length code, malformed block hash/block number/status/echo and dual-target receipts, wrong or unbound generic targets, unsupported method, transport failure — each keeps `applicationOutcome != APPLICATION_VERIFIED` and validates against the schema. Adversarial mainnet-vs-testnet substitution tests assert one-call stop behavior; a static scan proves no helper source references any signing, broadcast or secret-handling surface (FR-008); `MINT` is a recognized-but-refused action kind that makes no network call. Every diagnostic test uses an injected mock transport: no test touches a real QIE endpoint, and no report is presented as live network evidence (T4/T9).

## Release blocker: contract-address identity validation

**BLOCKER (release, not implementation).** No ecosystem contract may be promoted to `VERIFIED` in any claim, capability, address record or skill reference until address identity validation exists beyond code presence. `eth_getCode`-style observations prove bytecode exists at an address on a chain; they never prove issuer identity, ABI correspondence or product ownership. The existing `checkAddresses` gate requires issuer and ABI provenance sources, a matching reviewed chain-observation run, and check/expiry metadata before `AddressRecord.status: VERIFIED` is accepted, and the canonical address and runtime-evidence collections remain empty. Before any ecosystem contract address is published: (a) issuer and ABI sources must be recorded and reviewed, (b) a scoped chain observation must bind `(chain_id, address)` to the expected deployment, (c) human review must confirm the sources are the actual issuer's official channels, and (d) multi-source conflict handling must exist. Until then every ecosystem address stays `UNKNOWN`/`CLAIMED` and the router instructs agents never to generate a plausible-looking address. This blocks B08 promotion and any P1 integration recipe (FR-004, FR-017, FR-021, NEG-06).

Coding agents must refuse to hallucinate or generate plausible contract addresses for DEX routers, tokens, or pools.

**QIE Wallet extension specifics and limitations.** QIE Wallet extension v4.2.2 is documented via official docs and Chrome Web Store metadata. No official subgraph deployment on The Graph, Envio, or Goldsky is substantiated (`indexer-query: UNKNOWN`); safe direct JSON-RPC `eth_getLogs` with bounded block ranges (2,000–5,000 blocks) is established as the recommended alternative.

**Cosmos native layer vs EVM smart contracts.** Clear operational boundaries are established between native Cosmos SDK operations (`qied tx staking delegate`, chain ID `qie_1990-1`, base denom `aqie`) and EVM smart contracts (chain ID 1990, `0x` addresses). The native conversion precompile `0xD4949664cD82660AaE99bEdc034a0deA8A0bd517` is documented for converting Cosmos `aqie` to EVM ERC-20 tokens.

**Network substitution refusal and legacy chain conflict resolution.** Strict refusal rules prevent cross-network fallback between Mainnet (1990) and Testnet (1983). Legacy chain IDs 5656 and 9731 are classified as `DEPRECATED`. The conflict with external aggregators displaying 5656 is classified as `CONFLICTED` and resolved authoritatively in favor of canonical V3 Mainnet (1990).

**Minimal, backwards-compatible schema evolution.** Schema and policy versions advance to `1.3.0`. Changes are minimal: added `"ecosystem"` to `skill.schema.json` `generated_references.items.enum`, and added `"data/ecosystem-catalogue.json"` to `manifest.schema.json` `snapshot_path.enum`. Release context is versioned to `0.5.0-ecosystem.1`.

## B08 remediation decisions: independent-audit response (release 0.5.1-ecosystem.1, schema 1.4.0)

Two independent reviews (`docs/audit/QIE_Forge_B08_Independent_Review.md`, `docs/audit/QIE_Forge_B08_Consolidated_Findings.md`) held B08 acceptance for knowledge-integrity, provenance, and operational-guidance defects. All findings were reproduced against the workspace and are resolved as follows; no finding was dismissed.

**Canonical network facts are derived, never restated.** The ecosystem catalogue's network section is now a projection of the selected canonical claim records (chain IDs, RPC URLs, explorers, symbols, faucet) with their stored statuses and source citations. The renderer contains no RPC or explorer hostname. The authored decision guide uses the same canonical values (`rpc1mainnet.qie.digital`, `rpc1testnet.qie.digital`, explorers `mainnet.qie.digital` / `testnet.qie.digital`, re-verified against S03 on 2026-10-20); the non-canonical `rpc-main1`/`rpc-testnet`/`qiescan.org` hosts are gone from all published artifacts, and regression tests forbid their return.

**Compatibility views are operation-scoped projections of canonical records.** The hand-maintained product summary (independent statuses and descriptions, including a `DOCUMENTED` generic-wallet verdict and an uncatalogued precompile verdict) was deleted. The catalogue overview is one row per canonical capability (tool + operation + network + version + limitation), with statuses computed by the shared non-promoting effective-status evaluator against the frozen build clock. Mutation tests prove a canonical status change always projects into the published output.

**Category membership is canonical data.** Capabilities now carry a required `category` field validated against a canonical enum (`networks`, `wallets`, `frameworks`, `identity`, `explorers`, `defi`, `bridges`, `oracles`, `indexing`, `native-cosmos`). Substring matching is gone: QIEDex operations are `defi` (never native Cosmos), `indexer-query` is discoverable under indexing, and unknown/missing categories fail the build. This required field, and the schema/policy version, advance to `1.4.0`.

**The address-identity release blocker is enforced end-to-end.** The decision guide's Case B now carries the full gate (issuer provenance, ABI provenance, scoped `(chain_id, address)` identity observation, human review, conflict checks) and states that an explorer page, a successful receipt, or nonempty bytecode never establishes issuer/ABI/product identity. The catalogue publishes no contract address literal while the address inventory is empty, and a mutation test injects a source-claimed address to prove the renderer never turns it into an executable recommendation. The source-claimed conversion precompile from S16 stays unpublished until the blocker is satisfied.

**Source identities are reconciled to canonical data.** The evidence ledger previously swapped S08/S09 and mislabelled S12–S15/S18 relative to `knowledge/sources.yaml`; the ledger is now generated-adjacent, and a consistency test parses it and requires exact ID-to-URL equality with canonical data (with adversarial swap tests). S19 now carries the complete Chrome Web Store URL including the extension identifier. The Remix deployment guide was re-reviewed and added as genuine T1 source S21, so `remix-deploy` cites specific reviewed evidence instead of the documentation root; the canonical S08 title was corrected to match its URL.

**Operational certainty was removed where evidence does not exist.** The fixed native staking fee was replaced by an explicit placeholder plus a rule against hardcoding fees; the `eth_getLogs` guidance no longer asserts a 2,000–5,000 block bound (no QIE provider limit has been measured — probe, then bound); indexer language now says coverage is unsubstantiated in reviewed sources rather than categorically absent; local Solidity/EVM-target guidance (`shanghai`, Foundry replay) is labelled LOCAL_REPLAY-derived, not documented QIE support; the Hardhat example matches the official guide (Solidity 0.8.20, no invented EVM target).

**Evidence documents are generated from canonical records.** `docs/evidence/b08/capability-catalogue.md` is rendered by `scripts/lib/evidence-doc.mjs` (`npm run docs:generate`, checked by `npm run docs:check` and the test suite); the reported status counts in this milestone report are computed, not copied, and the counts table is cross-checked against canonical data by test. All B02–B07 regressions, the nine published skills, the B06 read-only diagnostics, the B07 recipes, and the deterministic packaging/drift architecture are preserved unchanged.

## B08 final-audit remediation decisions: provenance, projection and authored-literal control (release 0.5.1-ecosystem.1, schema 1.4.0)

A final independent audit (`docs/audit/QIE_Forge_B08_Final_Independent_Audit.md`) reviewed the remediated bundle and found the original B08 defects substantially closed, but held sign-off on three focused release gates. All three are resolved below; the B02–B08 defect classes remain closed and no skill had to be rewritten.

**Release timestamps are grounded in real time (F-FINAL-01).** The audit showed the release context claimed `built_at: 2026-10-20T08:00:00Z` and source S21 a review at `2026-10-20T06:00:00Z`, both later than the archive's own existence. Those were future dates, not a timezone reading, and a passing `build:check` never validated them. The release context is re-cut to the actual build time (`2026-10-19T22:35:15Z`), and S21 carries the review time that was actually observed (`2026-10-19T21:37:00Z`): the Remix deployment guide was re-retrieved and its content confirmed — the guide specifies an `Injected Web3` environment, and states no compiler version and no EVM target, exactly as the canonical record says. A release-cut chronology gate (`scripts/lib/chronology.mjs`) now compares the release cut and every source review timestamp against the real wall clock with a documented five-minute clock-skew tolerance, and the deterministic knowledge validators keep a separate injected-clock path so frozen fixtures never depend on real time. No timestamp is invented to make a check pass: when a review time is unknown it is recorded as `null` and the dependent operation stays conservative.

**One effective-status projection for every developer-facing verdict (F-FINAL-02).** The compatibility matrix published the stored status while the catalogue published the effective status, so an expired record would have produced two different support verdicts inside one bundle. Every renderer now projects through the same non-promoting effective-status evaluator at the same frozen build clock, and both values are published side by side, explicitly labelled `Stored Status` and `Effective Status`. The authored framework matrix uses the same projection, so an authored page cannot disagree with a generated one. A mutation test expires a documented capability and proves the catalogue, the matrix and the decision guide all downgrade together.

**Authored network facts are placeholders, and every published URL is traceable to canonical data (F-FINAL-03).** The authored decision guide and skill entry now state canonical endpoints, chain identifiers and capability statuses only through placeholders that are resolved from the skill's own canonical snapshot at build time: `{{claim:<network_id>:<predicate>}}`, `{{hex:<network_id>:<predicate>}}`, `{{stored:<capability_id>}}` and `{{effective:<capability_id>}}`. The grammar is fixed and strict — an unknown kind, a malformed claim token, a token matching no canonical claim, and a token naming no selected capability all fail the build instead of publishing as literal text. A build-time traceability gate now rejects any authored or published absolute URL whose host no canonical record attests, and rejects the endpoints this release retires, so a hand-edited stale endpoint in the authored guide fails the build. The gate is scoped deliberately: authored ecosystem content must have every absolute URL canonical, while a published bundle may still link to third-party reference material such as an EIP or a toolchain manual, because such a link is not a claim about QIE. The QIE-owned domains are derived from the canonical claim values rather than hand-listed, so the rule cannot itself drift.

**The release gate is honest about what it did not do.** No QIE RPC endpoint was contacted, no transaction was signed or broadcast, no wallet extension was loaded, and no capability was promoted to `VERIFIED`. The chronology gate proves only that recorded timestamps are not in the future; it does not attest that a source was read, and the source ledger remains the record of what was reviewed.

## B08 re-audit decisions: guard-locking the authored projection and the executed evidence

A re-audit of the remediated tree (`docs/audit/QIE_Forge_B08_Final_Remediation_Reaudit.md`) accepted all three findings as closed and found one release-sign-off gap in the guard itself: the placeholder mechanism prevented a *canonical change* from silently staling the authored guide, but nothing prevented a *handwritten literal* from re-entering the authored guide. One token edit could publish a hand-written chain ID or a support verdict that contradicts the canonical record, with a green build and a green suite. That gap is now closed, and the executed evidence is regenerated as a reproducible step.

**Authored canonical facts are guard-locked, not merely projected.** A new build-time gate (`assertNoHandWrittenCanonicalFacts` in `scripts/lib/canonical-facts.mjs`) runs on authored content with the placeholders removed, so it sees only what a human typed, and rejects three families: a chain identifier (decimal or `0x`-hex) written literally in a line that talks about a chain or a network; a canonical endpoint written literally instead of projected; and a support verdict written by hand — after `status:`/`verdict:`, after a canonical capability identifier, or next to a canonical capability or tool identifier whose canonical statuses do not include it. A general statement about the status vocabulary ("treat an unspecified version as UNKNOWN") names no canonical record and stays allowed, so the gate does not force prose into placeholders it cannot project. The one hand-written canonical endpoint the guard found in the published guide (the explorer link in the address-identity section) was replaced with a placeholder; the rendered output is byte-identical, so the published bundle did not change.

**The chronology rule has one implementation and one tolerance.** The release-cut gate and the knowledge validator previously carried two copies of the same rule with two tolerance constants. `scripts/lib/chronology.mjs` is now the only implementation: it collects the problems, the release path and the knowledge validator both call it, and the knowledge validator passes an injected clock so the frozen fixtures never depend on the wall clock. The knowledge suite is now hermetic — it validates against a fixed clock — while the real-clock behaviour stays covered by `tests/chronology.test.mjs`. An unknown review time (`null`) is legal in both: it is not a timestamp, so it can neither be in the future nor postdate the release cut, and the dependent operation stays conservative.

**The projection is carried by the published snapshot.** The effective status and its reason are computed once per release, at the frozen build clock, and attached to every claim and capability in the published knowledge snapshot. Every published view — the ecosystem catalogue, the compatibility matrix, the router coverage map, the network profiles, the selected-evidence pages and the authored framework matrix — reads that one value, so two views of the same capability cannot disagree. The canonical records in `knowledge/*.yaml` are unchanged: the projection is derived output, not canonical data, so the schema and policy version stay at `1.4.0`. A domain's `verification_status` is deliberately **not** projected: a domain is verified by scoped validation runs rather than by an expiry window, and the canonical validator already requires that evidence, so projecting it would publish a wrong verdict.

**The executed evidence is regenerated, not hand-copied.** `npm run verify:evidence` runs every gate — lint, knowledge and bundle validation, evidence-document generation and drift check, the deterministic build and its drift check, the full test suite, the coverage run and the Skills CLI installation fixtures — and writes the complete output of each run to `docs/evidence/b08/<gate>.txt` with the command, the Node version and the UTC time. The milestone reports quote executed numbers, so the same script compares those quoted figures against the logs the run just wrote and fails when they disagree. The comparison lives in the script rather than in the suite on purpose: the logs are written by a run of the suite, so a suite that asserted against them could never bootstrap a changed test count.

**What still cannot be verified locally.** The chronology gate proves that recorded timestamps are not in the future; it does not attest that a source was read. The traceability gate proves that a published QIE endpoint is attested by canonical data; it does not prove the endpoint is reachable, correct or live-verified. The 20/20 installation fixtures use the local Skills CLI against a local directory with a network-deny guard — that is not a published-git-source install and not public-distribution acceptance, and the official Agent Skills validator has still not been run.

## B09 decisions: content-addressed release identity, verifier-bounded updates and explicit rollback

**The suite identity is content-addressed, not a second human version.** B09 adds a required `release_id` to every generated manifest. It is the SHA-256 of a canonical JSON projection containing the frozen release version, schema version, build timestamp and every non-manifest file in every published bundle. `MANIFEST.json` is excluded because the identity is carried inside that manifest. Two builds with identical inputs produce the same identity; any covered content change, added or removed bundle changes it. The human release version remains `0.5.1-ecosystem.1` and the canonical knowledge/policy schema remains `1.4.0`; B09 changes packaging metadata, not QIE knowledge. `package-lock.json` was aligned to the already-declared package version so the lock and package identity no longer disagree.

**Suite coherence is a build/validation property before it is an installation property.** `validate-skills.mjs` now requires the published directory set to equal the enabled catalogue, requires all nine manifests to agree on release version, schema version, build timestamp and `release_id`, and recomputes the identity from the published bytes. A hand edit, a stale bundle or a mixed build therefore fails `npm run validate` and `npm run build:check`, not merely a post-install check.

**The pinned CLI is left as the installer and updater.** B09 adds a read-only `scripts/verify-installed-release.mjs` instead of a Forge-specific updater. It recomputes per-file SHA-256 and the suite identity from the installed tree, verifies knowledge and policy digests against the packaged snapshot, and reports missing/extra files, malformed manifests, legacy manifests without `release_id`, mixed release identities, mixed release/schema versions and incomplete suites. It exits 1 on any problem. This is necessary because Skills CLI 1.7.2 does not validate bundle manifests during install or update.

**Installed metadata is untrusted input.** The verifier validates the full manifest schema, restricts `snapshot_path` to published snapshot paths, requires the snapshot in both `manifest.files` and the walked inventory, checks containment before reading, rejects symlinked manifests and entries, enforces size ceilings, and returns generic diagnostics rather than parser excerpts or file content. The B09 independent audit demonstrated that the earlier verifier could follow `../` to an outside file and echo part of its invalid JSON; the regression suite now covers relative traversal, absolute paths, symlink escapes, unreadable and oversized snapshots, and parser-error redaction.

**Canonical scope and projections are explicit.** The verifier uses the trusted nine-name contract in `scripts/lib/release-contract.mjs` (cross-checked against the enabled catalogue by `validate-skills.mjs`). Unrelated agent skills are ignored, a canonical name that is a symlink or malformed bundle is rejected rather than silently skipped, and `--expect-suite` must find the exact canonical set. Each canonical `SKILL.md` frontmatter name must match its directory. When `.agents/skills` is the root, a sibling `.claude/skills` projection is checked for relative link correctness, exact canonical target, or byte alignment when copied; an unrelated-only Claude directory is skipped so Codex-only installs remain valid.

**Internal coherence is not publisher authenticity.** A self-consistent tree can still be fabricated. `COHERENT_FULL_SUITE` reports only that the exact canonical inventory, frontmatter, hashes, snapshots and identity recompute coherently. `publisherAuthenticity` remains `NOT_ESTABLISHED` unless the caller supplies a trusted `--release-id`; only then can it report `PINNED_MATCH` or `MISMATCH`. The B09 independent audit reproduced a recomputed fake nine-name suite; the corrected verifier rejects the missing canonical router and requires the trusted pin to distinguish a coherent-but-untrusted tree.

**Structural completeness and successful verification are separate booleans.** `inventoryComplete` means the exact canonical nine bundles are present with readable file inventories; it can remain true for a release rejected by a wrong pin, a mixed identity or a broken Claude projection. `payloadIntegrity` reports SHA-256 agreement for declared non-manifest files. `releaseCoherence` reports the schema, inventory, snapshot, provenance, identity and projection contract, excluding only the optional pin comparison. `verificationComplete` requires both full canonical inventory and zero blocking problems. The legacy `suiteComplete` field is a fail-closed alias of `verificationComplete`, not structural shape; it is always false for `REJECTED` and `COHERENT_PARTIAL` results.

**A release-ID match authenticates payload identity, not manifest-only metadata.** The release identity excludes `MANIFEST.json` to avoid self-hashing. The verifier derives `sources_checked_at` from the selected snapshot's source review timestamps and rejects a manifest value that differs, but that consistency check does not put the manifest field inside the content address. Reports expose `authenticityScope: PAYLOAD_IDENTITY_ONLY`, `provenance.manifestMetadataAuthenticated: false` and the per-skill derived/original provenance values. Mutating the manifest timestamp alone changes the report to `REJECTED` with `SOURCES_CHECKED_AT_MISMATCH`, while payload integrity remains `VERIFIED` and a trusted pin can still match the unchanged payload identity. Authenticating manifest-only metadata requires a separately trusted manifest or signed canonical index, not a self-contained manifest.

**Observed CLI behavior defines the supported update contract.** With the pinned CLI, a Git source records its requested ref in `skills-lock.json`; `update` follows a mutable branch, leaves a pinned tag or full SHA unchanged, and requires an explicit reinstall to change pins. A local-directory source is install-only: `update` exits 0 and prints `No installed skills found matching` rather than updating. `update` does not preserve a prior `--copy` projection for Claude Code; it installs the default symlink projection, while `.agents` remains the canonical copy.

**Rollback is explicit reinstallation, not an atomic transaction.** The known-good pinned ref is installed again with the same skill selection. Copy fidelity is restored by adding `--copy`; the verifier then proves the exact files and identity. A failed update after source removal leaves the previous tree intact, but a corrupt source that the CLI successfully installs is only detected after the fact by the verifier. True process-kill interruption and automatic pre-update backup are not implemented.

**The authenticated private GitHub proof does not equal a B09 remote release.** The private repository was installed at an immutable full commit SHA using the existing GitHub credential helper. That commit contains the B08 bundles, so the verifier correctly reports nine legacy manifests without `release_id`; all file, knowledge, policy and snapshot hashes match, and a pinned update reports `All project skills are up to date`. No B09 commit, tag or release was pushed. B09 therefore remains PARTIAL for remote distribution, and public installation remains unclaimed.

**No capability status changed.** B09 exercised packaging, Git refs, installer projections, digest verification and rollback only. It did not contact a live QIE RPC endpoint, load a wallet, sign or broadcast a transaction, deploy a contract or promote any QIE capability to `VERIFIED`.
